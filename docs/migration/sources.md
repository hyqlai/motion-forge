# 现有能力与迁移策略

## 来源特点

| 来源 | 主要能力 | 迁移方式 |
|---|---|---|
| `brewreel` | 结构化 Brief、公共镜头、讲课版式、口播模板、事实与合规校验 | 镜头逐步拆成独立场景/组件卡，保留结构化输入和校验思想 |
| `deepseek-opus-motion-skill` | 自由设计契约、SVG/材质/角色/形变、代码配乐和评审 | 迁移运动原语与可复用组件，不搬整套单片模板 |
| `onetake` | 纯时间函数、一镜到底、承接、运镜、运动模糊和量化验收 | 将 JS 运动能力改写为 Remotion 可用的纯函数与卡片 |
| `video-shotcraft` | 产品网页采集、镜头卡、Gallery、节拍同步和工作台 | 全量纳入镜头卡清单，按新 props/时间/主题契约迁移 |
| `video-talkcraft` | 口播时间戳、语义选卡、人物安全区和多类动效卡 | 全量纳入卡片清单，保留使用场景并解除示例内容耦合 |

## 全量迁移原则

1. 先建立机器可读清单，再分批实施；复制源码不等于迁移完成。
2. 近似卡先全部保留并建立相似组，不未经预览对比就删除。
3. 每卡保留原始来源和参考实现路径，便于回查。
4. 迁移后必须有独立预览、场景说明、props、时长策略和 QA。
5. 原卡中的示例文案、固定截图、绝对坐标和业务样式不能直接成为新卡硬依赖。
6. 一张卡未通过独立渲染和参考对比时，状态只能是 `pending` 或 `migrating`，不能标为 `ready`。

## 清单生成

在 Motion Forge 根目录运行：

```bash
npm run cards:inventory
```

命令扫描当前工作区内的源项目，将结果写入 `docs/migration/cards.json` 和 `docs/migration/inventory.md`。所有产物保留在本项目目录内。
