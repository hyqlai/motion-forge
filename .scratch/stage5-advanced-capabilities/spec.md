# 阶段 5：高级能力与完整片种

Status: ready-for-agent

## Problem Statement

Motion Forge 已能生成自包含视频工程，并通过 G1/G2 门禁、目标 Film 校验、工作台写回和 Three.js 软件渲染完成基础制作链路。但当前项目仍主要依赖硬编码草稿：旁白需要用户自行准备，音频只有单轨 BGM，歌曲无法自动转写和逐行对齐，外部图片与音乐没有真实 Provider 实现，每次修改都需全量重渲，最终交付也缺少统一 QA 与完整交付包。用户无法从主题、歌曲或素材顺畅得到一部具备真实音画内容、可编辑、可增量迭代、可独立交付的视频。

## Solution

按“Provider 基础设施 → 内容策划 → 多轨音频 → 增量渲染 → 导出与 QA → 高级场景验证”的顺序补齐高级能力。TTS/ASR 与素材获取采用可替换 Provider，首个实现分别为 Fish Audio、Pexels 和 Pixabay Music，密钥仅从环境变量读取。内容策划由技能模板配合 Agent 自身 LLM 完成，不引入外部 LLM API。Film IR 扩展为 BGM、Voice、SFX 三轨，工作台可编辑这些轨道并复用现有写回与审批重置。渲染支持场景哈希驱动的增量渲染，最终导出包含 MP4、可编辑工程、QA 报告与素材清单的完整交付包。

## User Stories

1. 作为视频制作 Agent，我希望通过统一 TTS Provider 接口生成旁白，以便不为每个供应商重写制作流程。
2. 作为视频制作 Agent，我希望通过统一 ASR Provider 接口转写歌曲和口播，以便获得可复用的文本与时间信息。
3. 作为视频制作 Agent，我希望先使用 Fish Audio 的 TTS/ASR 实现，以便快速建立可用能力，同时保留替换供应商的空间。
4. 作为项目维护者，我希望供应商密钥只从环境变量读取，以便密钥不进入代码、日志、工程包或 Git。
5. 作为视频制作 Agent，我希望通过 Pexels 搜索并下载图片到项目本地，以便画面素材不依赖运行时远程 URL。
6. 作为视频制作 Agent，我希望通过 Pixabay Music 搜索并下载 BGM 到项目本地，以便音频可随独立工程迁移和渲染。
7. 作为视频制作 Agent，我希望下载后的素材沿用现有本地资产登记与校验，以便 Provider 不绕开独立工程约束。
8. 作为视频制作 Agent，我希望主题输入能触发结构化内容策划，以便从一句主题得到有叙事弧线的分镜，而不是固定三镜占位文本。
9. 作为视频制作 Agent，我希望内容策划模板直接给出每镜的旁白、上屏文字、视觉描述、动效建议与时长，以便其可转换为 Film IR 并进入 G1。
10. 作为视频制作 Agent，我希望内容策划使用我自身的 LLM 能力，以便不引入额外 LLM API、密钥和计费依赖。
11. 作为视频制作 Agent，我希望 URL 输入能结合已抓取的来源内容完成策划，以便上屏文字和事实不脱离来源。
12. 作为视频制作 Agent，我希望歌曲输入能自动 ASR 转写，以便生成歌词和音乐结构分析材料。
13. 作为视频制作 Agent，我希望 ASR 词级时间戳能按停顿和语义分为逐行歌词，以便每行歌词映射到文字动效时间段。
14. 作为视频制作 Agent，我希望逐行歌词保存为项目分析产物，以便后续修改分镜时无需重复转写。
15. 作为视频制作 Agent，我希望能按所选 TTS Provider 为每镜旁白生成音频，以便样板镜和全片具有真实配音。
16. 作为视频制作 Agent，我希望 TTS 音频按项目规则落盘并关联到对应分镜，以便 Voice 轨道随工程独立渲染。
17. 作为视频制作 Agent，我希望 Film IR 同时描述 BGM、Voice、SFX 三条轨道，以便音画关系成为可校验的事实源。
18. 作为视频制作 Agent，我希望 Voice segment 能关联 sceneId、时间区间与文本，以便渲染器准确放置每段旁白。
19. 作为视频制作 Agent，我希望 SFX event 能关联 sceneId、局部帧和音效类型，以便转场或重音处准确触发音效。
20. 作为视频制作 Agent，我希望渲染器按时间线混合三轨音频，以便最终 MP4 保留正确的音量、起止和同步关系。
21. 作为工作台用户，我希望查看并调整 BGM 音量与循环设置，以便不必手工编辑 JSON。
22. 作为工作台用户，我希望查看并编辑 Voice segment 与 SFX event，以便修正旁白和音效时序后重新预览。
23. 作为工作台用户，我希望音频修改也通过现有 Film IR 写回流程保存，以便审批状态和版本行为与其他编辑一致。
24. 作为视频制作 Agent，我希望修改已审批音频后原审批失效，以便新音画方案重新经过 G1/G2。
25. 作为视频制作 Agent，我希望系统为每个场景计算内容哈希，以便识别真正发生变化的分镜。
26. 作为视频制作 Agent，我希望增量渲染只处理变化场景及受影响转场边界，以便修改一镜时不重渲整片。
27. 作为视频制作 Agent，我希望未变化场景复用已验证的帧缓存，以便增量结果与全量渲染保持一致。
28. 作为视频制作 Agent，我希望缓存失效能由内容哈希准确判断，以便不会把旧画面错误复用到新版本中。
29. 作为视频制作 Agent，我希望渲染成功后更新场景哈希记录，以便下一次增量渲染有可靠基线。
30. 作为视频制作 Agent，我希望最终导出前自动生成 QA 报告，以便集中确认场景、卡片、素材、音频、帧数和渲染结果。
31. 作为视频制作 Agent，我希望 QA 报告同时提供机器可读和人工可读形式，以便自动验收与人工复核共用一份证据。
32. 作为视频制作 Agent，我希望通过单个导出命令得到完整交付包，以便视频可直接播放、工程可继续编辑。
33. 作为接收交付包的用户，我希望包内包含 MP4、可编辑工程、QA 报告和素材清单，以便不访问技能目录也能理解和运行项目。
34. 作为视频制作 Agent，我希望高级场景能力复用已验收的长镜头、SVG 形变和 Three.js 动效卡，以便不重复建设已有视觉能力。
35. 作为项目维护者，我希望每个阶段都经过类型检查、现有 validate/build 与 CLI 端到端验证，以便高级能力不会破坏既有制作链路。
36. 作为项目维护者，我希望外部 HTTP Provider 在测试中可被 mock，以便验收不依赖真实 API 额度或网络状态。

## Implementation Decisions

### 1. Provider 基础设施

- 新增独立 TTS Provider 与 ASR Provider 接口和注册机制，接口边界与现有 Resource Provider 保持一致：调用方只依赖能力契约，不依赖供应商实现。
- TTS Provider 接收文本与音色、格式、韵律等选项，返回音频数据；ASR Provider 接收本地音频路径与语言、时间戳等选项，返回全文、时长和词级 segments。
- Fish Audio 作为两类 Provider 的首个实现。TTS 使用其文本转语音接口，ASR 使用其语音识别接口；认证从环境变量读取，默认模型分别为 `s2.1-pro` 与 `transcribe-1-pro`。
- 对认证失败、余额不足、并发限流、服务端错误建立明确错误分类；仅对可重试错误进行有限退避，禁止静默切换供应商或掩盖失败。
- 遵循 ADR-0001：TTS/ASR 能力内建于技能代码库，不调用外部技能。

### 2. Resource Provider 实现

- Pexels 实现图片搜索与下载，Pixabay Music 实现 BGM 搜索与下载，二者均实现现有 Resource Provider 接口。
- 搜索结果保留来源、标题、预览和授权相关元数据；下载落盘后才可进入 Film IR，渲染不得直接引用远程 URL。
- 外部输入和 Provider 下载统一经过项目本地素材目录、相对路径登记与目标 Film 校验。
- CLI 创建流程提供可选的 TTS Provider 与 BGM 搜索入口，未提供密钥或明确启用外部服务时保持现有本地草案行为，不自动产生付费调用。

### 3. 内容策划与歌词对齐

- 新增结构化内容策划模板，约束叙事弧线、分镜字段、时长分配、视觉描述和动效选择，供 Agent 自身 LLM 使用。
- 遵循 ADR-0002：不引入外部 LLM API。内容策划输出必须经过 Film Schema、注册表与素材校验后才能进入 G1。
- 歌曲输入在可用 ASR Provider 时生成转写分析产物；词级 segments 按停顿、持续时间和文本边界组合为逐行歌词，保留每行起止时间。
- 歌词对齐结果进入项目分析目录，后续分镜与文字动效可引用，不将分析数据写死在场景组件中。

### 4. 多轨音频

- Film IR 音频模型从单一 BGM 扩展为 BGM、Voice、SFX 三轨，保持旧 Film IR 中仅 BGM 的兼容性。
- Voice 由若干 segment 构成，每个 segment 包含 sceneId、起止时间和文本；SFX 由若干 event 构成，每个 event 包含 sceneId、局部帧与音效类型。
- 渲染层按编译后的全片时间线换算 Voice 与 SFX 的位置，保持各分镜内部只使用局部帧的设计约束。
- 工作台增加三轨查看与编辑能力：BGM 音量/循环、Voice segment、SFX event；所有修改复用现有 Film IR 写回接口与审批重置，不建立第二份音频事实源。
- 目标 Film 校验补充三轨路径、时间区间、场景引用和本地文件检查。

### 5. 增量渲染

- 为每个场景计算内容哈希，输入包括场景结构、动效、公开 props、关联素材和音频引用；哈希不包含渲染时间、临时路径等易变元数据。
- 保存每次成功渲染的场景哈希与帧缓存，增量渲染时只重渲哈希变化场景及受影响的相邻转场边界。
- 未变化场景必须复用与目标版本匹配的缓存，禁止仅按场景 ID 复用旧帧。
- 渲染失败不更新哈希基线；全量渲染始终可用，增量渲染不能成为绕过 G1/G2 的通道。
- CLI 增加显式增量模式，默认行为保持可预测，输出中明确列出复用与重渲的场景。

### 6. QA 与交付包

- 导出前汇总 Film Schema、场景/卡片注册、素材本地化、三轨音频、帧数、门禁状态与视频解码检查，生成机器可读和人工可读 QA 报告。
- 新增单命令导出，生成包含 MP4、完整可编辑工程、QA 报告和素材清单的交付包；交付包不得包含密钥、缓存中的绝对路径或技能目录依赖。
- 高级场景阶段复用现有已验收卡片完成一镜到底、复杂 SVG 形变和高级 Three.js 的验证与制作指引，不为此另建场景框架。

## Testing Decisions

- 好测试只验证外部行为：CLI 是否接受/拒绝正确输入、生成的 Film IR 是否合规、真实产物是否存在且可解码、第二次增量运行是否复用未变化场景，不检查内部私有函数调用次数。
- 沿用当前最高层测试缝隙：`forge` CLI 在模板外临时独立项目中执行，配合现有 `validate`、TypeScript 检查与工作台构建，不引入新的测试框架。
- TTS/ASR/Resource Provider 通过可替换实现和本地 mock HTTP 服务测试成功、认证失败、限流与下载落盘，不依赖真实 API key、网络或计费额度。
- 内容策划以模板产物和最终 Film IR 为验收对象；歌词对齐以带已知时间戳的转写样本验证逐行分组，不要求真实歌曲调用。
- 多轨音频通过小型三轨 Film 验证 Schema、工作台 API 和真实 MP4 解码；抽样确认 Voice/SFX 的时序与场景边界。
- 增量渲染对同一项目连续运行两次：首次建立缓存，修改单镜后第二次仅重渲该镜与必要边界，未变化场景保留原缓存证据。
- 导出验收检查交付包清单、QA 结果、密钥/绝对路径扫描，以及在无技能目录环境下安装与渲染。
- 所有阶段完成后执行现有全量卡片校验、模板 Film 校验、TypeScript 与工作台构建，并使用 `swangle` 做含 Three.js 的真实渲染冒烟。

## Out of Scope

- 不调用外部 LLM API，不调用外部 TTS/ASR 技能，不在本期接入 Fish Audio 之外的第二家 TTS/ASR 供应商。
- 不实现任意数量的 DAW 音轨；本期仅支持 BGM、Voice、SFX 三轨。
- 不为长镜头、SVG 形变或 Three.js 重造新场景框架，不改写现有 265 张动效卡体系。
- 不引入新的单元测试框架或持续集成服务，不要求测试使用真实付费 API。
- 不实现云端多人协作、在线项目托管或用户权限系统，不改变本地独立工程的交付形态。
- 不承诺自动内容策划无需 G1/G2，任何自动生成内容仍必须经过用户确认。

## Further Notes

- 各步骤按依赖顺序独立交付，Provider 失败不得影响不使用外部 Provider 的既有本地工作流。
- 旧 Film IR 只含 BGM 的项目必须继续通过校验与渲染；新增 Voice/SFX 字段均为可选。
- 任何外部服务调用都应显式可识别、可关闭、可审计；密钥、原始音频和下载素材均按项目边界管理。
